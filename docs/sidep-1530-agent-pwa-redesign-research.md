## 1. Наш продукт: термины и роли

### 1.1 Термины (из агентского соглашения в Figma)

| Термин | Значение |
|---|---|
| Агент | Физ./юрлицо, привлекающее игроков и совершающее депозиты/выводы на их игровые счета за комиссию |
| Касса | Приложение (это и есть PWA), через которое агент проводит депозиты/выводы |
| Игрок | Клиент букмекера, конечный получатель депозита/вывода |
| Комиссия | Заработок агента с каждой транзакции |
| Выплата | Начисление заработка агента из внутреннего счёта во внешнюю платёжную систему агента |
| Агентская сеть | Совокупность агентов, привлечённых компанией |

Ключевое бизнес-правило: выплата комиссии — раз в неделю (среда), при пороге по объёму и минимум 1 депозите; порог и валюта — из большого списка (RUB/EUR/USD/UZS/NGN/KES и т.д.) — гео-покрытие продукта широкое.

### 1.2 Три роли PWA (по диаграммам с кик-оффа)

| Роль | Что это | Доступные сценарии | Ограничения |
|---|---|---|---|
| **Агент** | Основной, полноценный PWA | Авторизация → KYC (сторонняя форма) → принятие соглашения → пополнение своей кассы с игрового аккаунта (по флагу) → депозит/вывод игроку → история → статистика → вывод прибыли с кассы на игровой (автовывод / заявка на ручной вывод / история выводов) | — |
| **Закреплённая касса** | Урезанный PWA для суб-агента, кассу создаёт суперагент | Авторизация (логин фиксированный, пароль каждый раз новый — выдаёт суперагент) → принятие соглашения → депозит/вывод игроку → история → статистика | Нет KYC-шага, нет пополнения кассы, нет вывода прибыли на игровой — статистика «ограниченная, без прибыли» |
| **Суперагент** | Back-office для управления сетью закреплённых касс | Авторизация → KYC → соглашение → пополнение бэк-офиса → история пополнений бэк-офиса → пополнение закреп-кассы с бэк-офиса → список закреплённых касс → детали кассы → действия (пополнить/вывести/статистика/история/сброс пароля/блокировка) → выводы: с касс на бэк-офис (история выводов с касс + пакетный «вывод со всех касс» одним действием), с бэк-офиса на игровой (разрез «прибыль с касс» / «прибыль с суб[агентов]» → автовывод/ручная заявка/история) | Это уже фактически «мультикасса» — управление N кассами из одной точки входа |

**Вывод:** «агент с одной кассой» и «суперагент/мультикасса» — не два состояния одного экрана, а структурно разные конфигурации с разным деревом сущностей (агент → касса, vs суперагент → N закреплённых касс, каждая со своей историей/статистикой/паролем). IA редизайна должна закладывать переключение контекста «текущая касса» как сквозной паттерн. Диаграмма бэк-офиса дополнительно показывает разрез «прибыль с касс» vs «прибыль с суб[агентов]» как уже разные сущности — суб-агентская сеть может быть частично уже заложена в модель данных, стоит уточнить у разработки.

## 2. Наш продукт: визуальный аудит («Updated old design»)

Бренд подтверждён визуально на всех экранах: **1win / 1wincash** (логотип, футер «© 1win 2022», «1wincash | © 1win 2022» в сайдбаре). Никакой белолейбл-неоднозначности нет — это отдельный продукт, не связанный с конкурентами из раздела 5.

**Вход.** Логин / Пароль / «Забыли?» / «Войти», футер «© 2022 1win». Просто, без лишних элементов.

![Экран входа](/img/sidep-1530-figma/login.png)

**Что улучшить:**
- Нет быстрого повторного входа (биометрия / «запомнить меня») — при частых сессиях в течение дня (см. метрику retention/WAU в разделе 9.2) это лишнее трение на каждый вход.
- Нет переключателя языка на самом экране входа — при RTL-требовании (раздел 3, 6) агент-носитель арабского вынужден сначала войти на русском/английском интерфейсе, чтобы найти настройку языка.
- «Забыли?» ведёт только к паролю — не покрыт сценарий утери и логина, и пароля одновременно (актуально для роли «Закреплённая касса», где пароль выдаёт суперагент и меняется каждый раз, раздел 1.2).

**Правила и условия.** Модалка «Правила и условия работы 1wincash» поверх экрана входа — это не чекбокс в углу, а полноэкранная прокручиваемая карточка с текстом соглашения и кнопкой **«Принять и продолжить»** внизу. Реальный текст начинается с определений («Букмекерская компания», «Агент», «Касса», «Игроки», «Заработок») — совпадает с глоссарием в разделе 1.1.

![Модалка «Правила и условия работы 1wincash»](/img/sidep-1530-figma/rules-modal.png)

**Что улучшить:**
- Длинный юридический текст без структуры (нет оглавления/якорей по разделам) — агент физически не может быстро найти нужный пункт (напр. про запрет депозита на свой аккаунт), только листать целиком.
- Согласие оформлено одной кнопкой «Принять и продолжить» без промежуточных чекбоксов по ключевым пунктам — для критичных условий (напр. штрафы/блокировки) это слабое подтверждение осознанного согласия.
- Нет варианта открыть текст отдельно / скачать как PDF — юристу или самому агенту неудобно сверяться с текстом позже вне флоу входа.

**Пополнение счёта (депозит игроку).** Не отдельные экраны, а **прогрессивное раскрытие на одном экране**: сверху видны «Доступный остаток» и «Доступно для выплат» → поле ID + кнопка «Поиск» (у кнопки есть **лоадер** на время проверки — фидбэк уже есть) → после поиска ниже появляется блок «Результаты» с именем игрока и полем суммы (лимиты «От 100 до 10 000» показаны прямо под полем) → кнопка «Пополнить». Это короче и linear-нее, чем можно было предположить по одним названиям фреймов — **редизайну есть что терять**, если это заменить на визард в несколько отдельных страниц.

![Пополнение счёта — шаг 1: поиск игрока по ID](/img/sidep-1530-figma/deposit-1-search.png)

![Пополнение счёта — шаг 2: найден игрок, ввод суммы с лимитами](/img/sidep-1530-figma/deposit-2-amount.png)

**Что улучшить:**
- Нет сохранённых/недавних ID игроков — для агентов с частыми однотипными депозитами (бизнес прямо просил не замедлять этот сценарий, раздел 3) это самый очевидный источник ускорения; сейчас это только будущая фича «Избранные игроки» (раздел 4), а не часть текущего флоу.
- Нет инлайн-валидации формата ID до нажатия «Поиск» — ошибки ввода ID видны только постфактум (см. метрику «% ошибок ввода ID» в разделе 9.1), можно проверять формат прямо при вводе.
- Лимиты «От 100 до 10 000» показаны только текстом под полем — не подсвечиваются на самом поле при выходе за границы (нет live-валидации суммы), хотя именно это — вторая метрика ошибок в разделе 9.1.

**Выплата игроку (кэшаут).** Полноценный флоу с **проверкой кода**: список «Выплаты» (поиск по ID, статусы «Ожидание»/«Подтверждено», пагинация — в тестовых данных 17 страниц) → карточка «Детали» с данными игрока и суммой, кнопки «Отменить выплату» / «Готов выплатить» → шаг **«Проверка кода»** (агент вводит код, который называет/показывает игрок) → «Подтвердить и оплатить» → success-шторка «Платёж успешно совершён». **Это уже закрывает историю с двусмысленной confirm-формулировкой** (см. было в открытых вопросах) — направление денег и роль кода читаются однозначно по самому флоу.

![Список «Выплаты» с пагинацией и статусами](/img/sidep-1530-figma/payouts-list.png)

![Выплата — шаг 1: детали игрока и суммы, «Готов выплатить»](/img/sidep-1530-figma/payout-1-details.png)

![Выплата — шаг 2: проверка кода](/img/sidep-1530-figma/payout-2-code.png)

![Выплата — шаг 3: успешное завершение](/img/sidep-1530-figma/payout-3-success.png)

**Что улучшить:**
- Список «Выплаты» с 17 страницами пагинации не имеет видимого поиска/фильтра по дате или сумме — только по ID; агенту с высокой частотой операций сложно найти конкретную выплату задним числом.
- Кнопки «Отменить выплату» и «Готов выплатить» на экране деталей визуально равнозначны — деструктивное действие («Отменить») стоит визуально понизить в приоритете (второстепенный стиль), чтобы снизить риск случайного нажатия.
- В макете не видно error-состояния шага «Проверка кода» (что показывается при неверном коде) — это критичный для денежной операции сценарий, его нужно спроектировать явно, а не оставлять на потом.

**Терминологическая коллизия:** слово **«Выплата»** используется в макете сразу в двух разных смыслах — (1) по глоссарию по кик-оффу — это выплата комиссии агенту на внешний счёт; (2) в этом же экране — это выдача наличных игроку при кэшауте. Один термин на две разные операции — риск для UX-контента при редизайне (см. открытые вопросы).

**Что улучшить:** развести термины в самом интерфейсе, а не только в документации — например, «Кэшаут игроку» (или «Выдача игроку») для экрана из раздела 2 и отдельно «Мои выплаты» / «Заработок» для вывода комиссии агента на свой счёт. Сейчас это чисто текстовое решение UX writer’а (открытый вопрос 15), но без него любой редизайн интерфейса унаследует ту же двусмысленность.

**История.** Уже есть табы **«Все / Депозиты / Выводы»** и отдельная модалка «Календарь» с быстрыми пресетами дат («1 ноября 2021» / «18 ноября 2021»), помесячным календарём и кнопками «Установить дату» / «Сбросить». Разделение истории по типу операции, которое я ожидал не найти (было открытым вопросом) — **уже реализовано**.

![История с табами «Все/Депозиты/Выводы» и модалкой календаря](/img/sidep-1530-figma/history-calendar.png)

**Что улучшить:**
- Фильтр только по дате (календарь) и типу операции — нет поиска по ID игрока или сумме внутри истории, хотя именно это чаще всего ищут при обращении в поддержку (см. метрику «число обращений по флоу», раздел 9.3).
- Нет экспорта отчёта из истории — у конкурента Mobcash есть «скачать отчёт» прямо с главного экрана (раздел 5.1), у нас в этом макете такой возможности не видно.
- Нет визуального разделения "+"/"−" по типу операции (как у конкурента Б, раздел 5.2) — только текстовые табы; более явный визуальный код ускорил бы сканирование ленты глазами.

**Мультикасса уже живая, не только черновик.** На главном экране суперагента/бэк-офиса есть модалка **«Выберите кассу для пополнения»** — радио-список кассс («Cash_543», «Cash_5434339_hg404» и т.д.) перед действием. Это значит переключение между несколькими кассами — не гипотетическая будущая фича из раздела 4, а часть текущего продукта уже сейчас (для роли суперагента).

![Модалка выбора кассы для пополнения (мультикасса)](/img/sidep-1530-figma/multicashbox-picker.png)

**Что улучшить:**
- Имена касс технические и нечитаемые («Cash_5434339_hg404») — суперагенту, управляющему десятками касс, сложно опознать нужную по такому идентификатору; нужны либо человекочитаемые алиасы, либо доп. метаданные в списке.
- В списке выбора не видно баланса/лимита каждой кассы — агент выбирает вслепую, затем только после входа видит цифры; для быстрого решения «в какую кассу пополнить» это лишний шаг туда-обратно.
- Нет поиска/сортировки списка касс — при росте суб-агентской сети (раздел 4) плоский радио-список перестанет масштабироваться.

**Главный экран бэк-офиса.** Баланс + «Пополнить бэк-офис», два CTA («Пополнить кассу» / «Вывести с касс»), и **кольцевая диаграмма** прибыли за период с разбивкой ниже («Доступно для вывода с касс» / «...с субагентов», «Прибыль с депозитов» / «...с выводов» / «...с субагентов») — уже присутствует визуализация composition-типа, которую стоит учитывать в редизайне статистики (раздел 4).

![Главный экран бэк-офиса суперагента с кольцевой диаграммой прибыли](/img/sidep-1530-figma/backoffice-home.png)

**Что улучшить:**
- Диаграмма показывает только один период без сравнения (день/неделя/месяц) — фича «сравнение периодов» уже запрошена (раздел 4, «Развитие статистики»), но на этом конкретном экране её пока нет вообще.
- Разбивка «прибыль с касс» / «прибыль с суб[агентов]» — только текстовые цифры, не отражена в самой диаграмме — сейчас нужно сопоставлять числа под кольцом вручную, композиционная визуализация не показывает вклад каждого сегмента.
- Нет прямого перехода «показать по конкретной кассе» из этого агрегированного экрана — суперагенту приходится уходить в отдельный список касс и терять контекст сводки.

**Десктоп.** Sidebar-навигация (Пополнение счёта / Выплаты / История / Статистика) — **уже есть в текущем дизайне**, это не новшество из черновиков «Мультикассы» (см. правку в разделе 6).

![Десктоп-версия с sidebar-навигацией](/img/sidep-1530-figma/desktop-sidebar.png)

**Что улучшить:**
- Неясно, есть ли промежуточный breakpoint между мобильным таббаром и десктоп-сайдбаром (напр. планшет) — судя по структуре Figma, состояние «среднего» экрана не отрисовано, риск получить сломанную адаптивность в этом диапазоне.
- В sidebar нет точки входа под уведомления (иконка/бейдж) — фича «Уведомления» должна попасть в редизайн до релиза (раздел 4), но архитектурно место для неё в текущем sidebar не заложено.
- Sidebar дублирует состав таббара 1-в-1 без учёта того, что на десктопе у суперагента больше экранного пространства — можно было бы сразу показывать сводку/бейджи (кол-во касс, непрочитанные уведомления) прямо в самом меню, а не только названия разделов.

## 3. Ограничения и риски нашего продукта

**Ключевое ограничение с кик-оффа:** депозит и вывод нельзя усложнять и увеличивать по числу шагов — сейчас это короткий флоу (ID игрока → сумма → действие).

| Риск/ограничение | Почему критично |
|---|---|
| Депозит/вывод — не более текущего числа шагов | Прямое требование бизнеса, подтверждено дважды на кик-оффе |
| Скорость сериальных операций | Есть агенты, делающие много однотипных депозитов в день — редизайн должен ускорять, не замедлять повторный ввод |
| Обязательное подтверждение для денежных операций | Явно запрошено бизнесом как защита от случайных действий — конфликтует с «минимум шагов»; решать через качество экрана подтверждения, а не через его исключение. У выплаты игроку это уже решено через шаг «Проверка кода» (см. раздел 2) — важно не потерять этот механизм при редизайне |
| Слабый интернет у части агентов | Запрет на тяжёлые анимации/эффекты — ограничивает performance-бюджет редизайна |
| Необратимые действия (валюта кассы, генерация нового пароля для закреп-кассы) | Должны остаться явными, с предупреждением — нельзя «причесать» до одного тапа |
| Дублирование сущностей без дизайн-системы | Одинаковые по смыслу экраны/модалки повторены по 3–6 раз в разных состояниях («Выводы» ×6, «История» ×десятки, слои без осмысленных имён — `.`, `Title`, `info`) — до проектирования нужен аудит фактических состояний каждого повторяющегося экрана |
| Мобайл-браузер — приоритет, но не единственная платформа | PWA остаётся браузерным продуктом; большинство агентов заходят с телефона, но десктоп обязателен к проработке (вторичный приоритет) |
| RTL как полноценные отзеркаленные макеты | На кик-оффе отдельно уточнили: RTL нельзя закрыть только на уровне переменных дизайн-системы — нужны реальные отзеркаленные макеты для арабской локали в этом же релизе, не как доработка после |
| Дизайн-система — не обязателен 1-в-1 реюз текущей | Жёсткой привязки к полному переиспользованию текущей системы нет, можно рассмотреть более гибкое решение — но с учётом будущих фич/масштабирования и связи с общей стилистикой продукта |

**Где не хватает данных / нужны уточнения:**
- Нет аналитики (частота экранов, где агенты бросают сценарий, % ошибок ввода ID/суммы) — без неё риски выше нельзя приоритизировать по данным, только экспертно.
- Не хватает реального разреза «депозит vs вывод vs пополнение кассы» по частоте использования — с чего начинать оптимизацию скорости.
- Неясно, что означает флаг у пункта «Пополнить кассу с игрового аккаунта» («отображаем в зависимости от флага») — от чего зависит: от роли, от гео, от статуса верификации?
- Терминологическая коллизия «Выплата» (комиссия агента vs выдача наличных игроку) — см. раздел 2, нужно решение UX writer’а до формулировок в редизайне.

## 4. Как будущие фичи повлияют на архитектуру

Явно вынесенные вне скоупа SIDEP-1530 (будут отдельными задачами), но **архитектурно должны быть предусмотрены сейчас**:

- **Уведомления** — единственная фича, которая должна быть добавлена **до** релиза редизайна (см. ссылку на `[URD] Нотификация в PWA (1 итерация)` в брифе). Значит на архитектурном уровне уже сейчас нужны: точка входа (иконка/бейдж в хедере или сайдбаре), центр уведомлений как отдельный экран, разрешения на push в PWA (ограничения браузеров/iOS Safari — см. открытые вопросы).
- **Реферальная программа** — добавит уровень сущности «реферал» поверх иерархии «суперагент → закреплённые кассы». У конкурента Б (см. 5.2) это разделено на два независимых механизма (реферальная программа агентов и отдельный аффилиат-кабинет) — стоит заранее решить, нужны ли у нас оба, или один.
- **Профиль агента** — текущий профиль минимален; расширение, вероятно, потянет за собой репутационные метрики — стоит заложить гибкую структуру профиля, а не фиксированный набор полей.
- **Избранные игроки** — ускоряющая фича именно для сценария «много однотипных депозитов», который бизнес просил не замедлять. Технически — «сохранённые ID» с быстрым доступом из экрана депозита.
- **Развитие статистики** — запрошено сравнение периодов (день/неделя/месяц) и разрез «по субагентам». Нужна архитектура агрегатов минимум в 2 измерениях (время × сущность).
- **Субагентская сеть / мультикассы** — **уже частично спроектирована** в Figma (раздел «Мультикассы» на канвасах Mobile/Desktop): черновые экраны «Кассы» (список), «Касса» (детали), «Генерация логина и пароля» (3 варианта), переход навигации с нижнего таббара на **Sidebar** для десктопа/бэк-офиса. Это черновой материал для UX-этапа, не идея с нуля.

**Общий архитектурный вывод:** большинство будущих фич (мультикассы, реферальная сеть, суб-агенты) — варианты одной модели «владелец → подчинённые сущности с ограниченным доступом». Стоит с самого начала проектировать один переиспользуемый паттерн иерархии/делегирования, а не решать для каждой фичи заново.

**Выводы по конкуренту Б**

Хорошо:
- Однозначная формулировка вывода (явно понятно, кто кому платит) + поле «Код на получение» — хорошая практика подтверждения, концептуально похожа на наш шаг «Проверка кода» (раздел 2), можно использовать как дополнительное подтверждение того, что наш подход верный.
- Разделение «реферальная программа агентов» и «аффилиат-кабинет для трафика игроков» на два независимых механизма — чище, чем смешивать их в одну фичу (важно для раздела 4).
- История по сессиям («Текущая» / «Предыдущие») с явным +/−/% на каждой строке — более информативно, чем плоская лента по датам.
- Отмена операции свайпом с ограниченным окном и восстановлением лимита кассы — удобный и безопасный паттерн отмены, стоит рассмотреть для нашего продукта.
- Гибкая настройка платёжных методов агентом (тумблеры по конкретным банкам) — даёт агенту контроль без обращения в поддержку.
- Переключатель темы оформления (система/светлая/тёмная) — стандарт категории, которого пока нет у нас — стоит заложить в редизайн.

Плохо:
- Обучающий видео-формат «Инструкция пользователя» подаётся как часть самого интерфейса (скриншоты внутри плеера) — если это единственный способ онбординга, это тяжеловесно для мобильного слабого интернета и конфликтует с нашим ограничением «без тяжёлых эффектов, слабый интернет» (раздел 3).
- Маскировка ФИО получателя («A***ey P***ov») — плюс с точки зрения приватности, но по скринам не видно, как агент получает доступ к полному имени при необходимости сверки — стоит уточнить у разработки, не создаёт ли это риск ошибки при выплате не тому игроку.
- Push-уведомления игрокам инициируются самим агентом — по скринам не видно rate-limit/ограничений — риск спама или жалоб, если это не ограничено технически; важно продумать до реализации аналогичной фичи у нас.
- Много разноплановых пунктов (2FA, тема, язык, платёжные методы, push, рефералка, партнёрка) свалено в один раздел «Настройки» без видимой группировки — для наших будущих фич (раздел 4) стоит спроектировать иерархию заранее, а не добавлять по одному пункту в общий список.

### 5.3 Mobile-money agent apps (M-Pesa, Airtel Money, аналоги)
- Два режима подтверждения операции: **agent-initiated** (агент вводит сумму, клиент подтверждает по SMS/PIN) и **customer-initiated** (клиент называет агента, инициирует сам).
- Вывод часто защищён **кодом авторизации** от клиента (клиент генерирует код → агент вводит/сканирует) — потенциально снимает двусмысленность в подтверждении «кто кому платит».
- Обе стороны получают SMS-подтверждение — офлайн-совместимый канал доверия, важно для регионов со слабым интернетом.

### 5.4 iGaming affiliate-кабинеты (Track360, Cellxpert, irev и др.)
- Real-time commission dashboard и granular sub-affiliate tracking по каждому уровню сети.
- Мастер-партнёр видит агрегированную статистику по всей нижестоящей сети, но каждый суб-партнёр видит **только свой** трафик (data scoping по уровню) — прямая аналогия с «Закреплённая касса видит статистику без прибыли»; тот же принцип должен применяться к будущей суб-агентской сети.
- Риски мошенничества внутри сети (circular referrals) — уже отражены в нашем агентском соглашении («сговор», «депозит на свой аккаунт запрещён»). UX должен помогать соблюдать эти правила (напр. явно блокировать ввод собственного ID), а не полагаться только на юридический текст.

### 5.5 Что можно переиспользовать как идею
- Явный код/токен подтверждения для операций с деньгами между агентом и игроком (снимает двусмысленность «кто кому платит»).
- Скоуп доступа «видит только своё» как системный принцип для любой будущей иерархии (суб-агенты, рефералы).
- SMS/офлайн-дублирование подтверждений как fallback при слабом интернете.
- Разделение «реферальная программа агентов» и «аффилиат-кабинет для трафика игроков» на два независимых механизма (конкурент Б).

### 5.6 Что не подходит напрямую
- Тяжёлые real-time графики/визуализации, типичные для десктопных affiliate-дашбордов — конфликтуют с требованием лёгкости на слабом интернете и mobile-first приоритетом.
- Многоуровневые MLM-подобные деревья с глубокой вложенностью — наша модель (агент → закреплённые кассы → суперагент) пока двухуровневая.

## 6. Платформы, RTL, дизайн-система

- **Mobile-браузер — приоритет, десктоп обязателен.** PWA остаётся браузерным (не нативным) продуктом; большинство агентов заходят с телефона — десктоп важен, но вторичен по приоритету.
- **Десктоп не с нуля** — в Figma уже есть версии с Sidebar-навигацией (вместо таббара) для канваса «Мультикассы» / Desktop.
- **RTL — отзеркаленные макеты, не только токены.** Арабский уже широко представлен у конкурента Mobcash (4 региональных варианта) — аудитория есть, тестировать RTL post-factum поздно и дорого.
- **Дизайн-система — гибкое решение, но не в отрыве от бренда.** Полного реюза текущей системы не требуется, но новое решение должно учитывать будущие фичи/масштабирование и сохранять связь с общей стилистикой продукта. Судя по структуре Figma (десятки фреймов `.`, дублирующиеся модалки в 5-6 состояниях, слои `Title`/`info` без осмысленных имён) — системы компонентов по факту нет, так что «более гибкое решение» реалистично строить с нуля, с оглядкой на существующий визуальный язык. До проектирования нужен **аудит фактических состояний** каждого повторяющегося экрана.

## 7. Открытые вопросы

**К продукту**
1. Confirm-модалка вывода в нашем продукте — есть ли та же двусмысленность «кто кому платит», что показалась в аналогичном экране у Mobcash (см. 5.1)? Стоит свериться визуально в Figma / на реальном стенде.
2. Что значит «отображаем в зависимости от флага» для пункта «Пополнить кассу с игрового аккаунта» — от чего зависит флаг (роль/гео/верификация)?
3. Есть ли реальная аналитика использования экранов (Amplitude/GA/внутренняя) — можно ли получить частоты сценариев и точки отвала до старта UX?
4. В use-case диаграмме заявлено разделение истории на «все / депы / выводы» — стоит проверить, реализовано ли это в текущем PWA уже сейчас.

**К бизнесу**
5. Какой % агентов пользуется десктопом vs мобильным — оправдан ли полноценный десктоп-редизайн в этом релизе.
6. Есть ли утверждённые сроки/приоритет для реферальной программы и мультикасс относительно этого редизайна.
7. Нужен ли у нас отдельный аффилиат-кабинет для трафика игроков (по аналогии с «Партнерам» у конкурента Б), или только реферальная программа для агентов?

**К разработке**
8. PWA push-уведомления — какие технические ограничения на целевых платформах (особенно iOS Safari) уже известны для раздела «Уведомления»?
9. Насколько глубоко в бэкенде уже реализована модель «суперагент → N закреплённых касс» — это готовая API-модель, которую редизайн визуализирует, или потребуется что-то менять и в бэкенде?
10. Есть ли уже техническая возможность конфигурации платёжных методов агентом (по аналогии с «Настройка эл. платежей» у конкурента Б), или это будет совсем новый функционал?

**К дизайн-системе**
11. Есть ли (хотя бы черновая) библиотека компонентов отдельно от макетов конкретных экранов — судя по Figma, вероятно нет; кто владелец будущей дизайн-системы и на каком движке?
12. Насколько далеко можно отходить от текущей стилистики продукта в рамках «гибкого решения», чтобы это не воспринималось как разрыв бренда?
13. RTL-макеты нужны отзеркаленные — на какие конкретно локали (только арабский, или и другие потенциальные RTL-языки) рассчитывать уже в этом релизе?

**К UX writer**
14. Терминология «Касса / Закреплённая касса / Суперагент / Бэк-офис» — устоявшийся продуктовый язык или его тоже предстоит пересмотреть в рамках редизайна?
15. Формулировки денежных подтверждений («Вы уверены?», «Подтверждаете получение…») — нужен ли единый tone of voice для критичных операций, учитывая мультиязычность и то, что часть пользователей — не носители русского?

## 8. Итог

Продукт устроен как минимум в три структурно разных роли (агент / закреплённая касса / суперагент-бэкофис), и часть будущего скоупа (мультикассы, суб-агентская сеть) — не новая идея, а уже частично отрисованные черновики в том же Figma-файле. Главный риск редизайна — не визуальный, а системный: отсутствие единой дизайн-системы уже породило десятки почти-дублирующихся состояний одних и тех же экранов, и без их аудита UX-этап рискует переупаковать тот же хаос. Второй по важности риск — жёсткое ограничение «не увеличивать число шагов» в депозите/выводе, которое прямо конфликтует с пожеланием «обязательное подтверждение для критичных операций»; это должно решаться качеством экрана подтверждения, а не количеством экранов. RTL и мобайл-браузер — не будущие требования, а уже действующая часть продукта и рынка (см. конкурента Mobcash), которую нельзя игнорировать. Открытые вопросы в разделе 7 — то, что стоит закрыть до начала UX-проектирования.

## 9. Метрики и как их улучшить

**Важная оговорка:** по открытому вопросу 3 (раздел 7) у нас пока нет подтверждённой аналитики использования экранов. Метрики ниже — не текущие цифры, а предлагаемый набор для инструментирования **до** старта UX-этапа, чтобы редизайн опирался на данные, а не только на экспертную оценку.

### 9.1 UX/продуктовые метрики

| Метрика | Сейчас (baseline) | Цель после редизайна |
|---|---|---|
| Time-to-complete депозита (от открытия экрана до успеха) | Не измеряется; качественно флоу уже короткий — прогрессивное раскрытие на одном экране (раздел 2) | Не хуже текущего — ограничение «не увеличивать число шагов» (раздел 3); ускорение только за счёт избранных ID и инлайн-валидации, не за счёт удаления шагов проверки |
| Time-to-complete выплаты, включая шаг «Проверка кода» | Не измеряется; флоу длиннее (список → детали → код → успех) | Не хуже текущего — доп. шаг «Проверка кода» сохраняется ради безопасности; ускорение за счёт лучшего error-handling, не за счёт удаления шага |
| % ошибок ввода ID игрока (не найден / неверный формат) | Нет данных (открытый вопрос 3) | Заметное снижение за счёт инлайн-валидации формата до сабмита — точный % целевого показателя ставить после первого замера baseline |
| % ошибок ввода суммы (вне лимитов) | Нет данных | Снижение за счёт live-валидации лимитов прямо в поле ввода |
| Drop-off по шагам флоу депозита/выплаты | Не измеряется вообще — воронки нет ни по одному шагу | Полная воронка по каждому шагу + снижение отвала на самом слабом шаге (пока неизвестном без замера) |
| % отменённых операций после отправки | Нет данных; в текущем макете вообще нет механизма отмены (у конкурента Б есть, раздел 5.2) | Сначала измерить фактическую частоту нужды в отмене — только после этого решать, добавлять ли механизм |
| Время до первого успешного действия новых суб-агентов (онбординг) | Нет данных | Минимизировать за счёт понятного онбординга закреп-кассы (раздел 1.2, раздел 4) |

### 9.2 Бизнес-метрики

| Метрика | Сейчас (baseline) | Цель после редизайна |
|---|---|---|
| Объём депозитов/выводов через кассу (в разрезе агент / суперагент) | Есть в транзакционных данных, но не сведено к UX-метрикам интерфейса | Не допустить падения относительно текущего уровня при смене интерфейса — рост считается успехом, падение — прямой регрессией (раздел 3) |
| Retention агентов (WAU/MAU, частота сессий) | Нет данных | Рост, особенно у суперагентов — за счёт удобного управления сетью через мультикассу (раздел 4) |
| % агентов, достигающих еженедельного порога выплаты комиссии | Нет данных, хотя само бизнес-правило известно (раздел 1.1) | Рост доли за счёт видимости прогресса к порогу (уведомления/статистика, раздел 4) |
| Доля мобайл vs десктоп трафика | Нет данных (открытый вопрос 5) | Не «улучшение», а факт для обоснования бюджета — собрать до конца этапа 1 роадмапа (раздел 10) |
| Конверсия в реферальную программу / партнёрский кабинет (после запуска) | Метрика неприменима — фичи пока нет (раздел 4) | Появится только после запуска соответствующей фичи (этап 3 роадмапа, раздел 10); считать раздельно «реферальная программа» и «аффилиат-кабинет», если реализуем оба |

### 9.3 Метрики поддержки и качества

| Метрика | Сейчас (baseline) | Цель после редизайна |
|---|---|---|
| Число обращений в поддержку по флоу (депозит/вывод/создание кассы/смена пароля) | Вероятно, не сегментировано по флоу — нужно уточнить у поддержки | Снижение по экранам, которые сейчас чаще всего вызывают обращения — после первого замера станет видно, какие именно |
| % обращений, связанных с двусмысленностью термина «Выплата» (комиссия агента vs кэшаут игроку) | Нет данных — коллизия сейчас не размечена как отдельная категория тикетов | Стремиться к нулю после разведения терминов в интерфейсе (раздел 2, этап 1 роадмапа) |
| % оспоренных операций из-за необратимых действий (смена валюты кассы, новый пароль закреп-кассы) | Нет данных | Низкий процент — если он уже низкий, экран предупреждения уже работает и трогать его не нужно |
| Время решения тикетов по confirm-модалке вывода | Нет данных | Снижение, если двусмысленность «кто кому платит» подтвердится на этапе 2 роадмапа (проверка гипотез) |

**Как использовать этот раздел:** до начала UX-проектирования — завести события/трекинг под метрики из 9.1–9.3, которых сейчас нет (это прямое продолжение открытого вопроса 3 в разделе 7). После первых 2–4 недель редизайна в проде — сверить эти метрики с гипотезами «как редизайн должен её улучшить» из третьей колонки, чтобы подтвердить или опровергнуть решения, а не полагаться только на качественную оценку.

## 10. Роадмап

| Этап | Период |
|---|---|
| Этап 0. Дискавери | Завершён (этот документ) |
| Этап 1. UX-флоу трёх ролей и закрытие открытых вопросов | Недели 1–2 |
| Этап 2 (+бизнес, разработка). Проверка гипотез | Недели 2–3 |
| Этап 3. Визуальная концепция и дизайн-система | Недели 3–4 |
| Этап 4. Финализация макетов | Недели 4–5 |
| Буфер на риски | Неделя 5–6 |
| Этап 5. Дискавери (после запуска) | Недели 7–8, после релиза в проде |

**Этап 0. Дискавери.** Уже сделан — это и есть настоящий документ: визуальный аудит нашего продукта (раздел 2), конкурентный research (раздел 5), риски и ограничения (раздел 3), метрики (раздел 9) и открытые вопросы (раздел 7). Этап 1 стартует не с нуля, а с уже собранными фактами и найденными «что улучшить» — задача следующих этапов не искать проблемы заново, а закрывать то, что здесь уже найдено.

**Этап 1. UX-флоу трёх ролей и закрытие открытых вопросов.** Проектируем сценарии отдельно для агента, закреплённой кассы и суперагента — у них разное дерево экранов, а не один флоу с переключателем роли (раздел 1.2). Параллельно закрываем открытые вопросы к бизнесу и разработке из раздела 7: доля мобайл/десктоп трафика, приоритет реферальной программы, готовность бэкенда к модели «суперагент → N касс». Здесь же UX writer фиксирует термин «Выплата», разводя его на «кэшаут игроку» и «мои выплаты» (раздел 2) — это должно быть решено до макетов, а не по ходу отрисовки.

**Этап 2 (+бизнес, разработка). Проверка гипотез.** Проверяем на практике то, что пока остаётся предположением из research: есть ли у нашей confirm-модалки вывода та же двусмысленность «кто кому платит», что у Mobcash (раздел 5.1); тестируем RTL-версию с реальным носителем арабского языка, а не только технически зеркалируем макет; прогоняем core-флоу на throttled-соединении, чтобы ограничение по производительности (раздел 3) не осталось только декларацией. Сюда же подключаем бизнес и разработку — уточнить, нужен ли отдельный аффилиат-кабинет помимо реферальной программы (открытый вопрос 7), и насколько глубоко уже реализована мультикасса в бэкенде.

**Этап 3. Визуальная концепция и дизайн-система.** Фиксируем решение по дизайн-системе — без жёсткого реюза текущей, но и без разрыва с существующим визуальным языком (раздел 6). Здесь же собираются отзеркаленные RTL-макеты параллельно с LTR-версией, а не как доработка после. Визуально прорабатываются экраны мультикассы и бэк-офиса с уже найденными улучшениями: читаемые алиасы касс и баланс в списке выбора, разрез статистики по кассам/суб-агентам (раздел 2, 4).

**Этап 4. Финализация макетов.** Собираем финальные LTR + RTL макеты для P0/P1-экранов — вход, депозит, выплата с явным error-состоянием неверного кода, история с поиском и экспортом отчёта. Проходим design review и передаём в разработку. К этому моменту должна быть готова аналитика/трекинг (раздел 9) — чтобы измерять эффект с первого дня в проде, а не добавлять события постфактум.

**Буфер на риски.** Резерв на то, что не закрылось на предыдущих этапах: бэкенд не успел с моделью «суперагент → N касс», нужная RTL-локаль требует больше валидации, чем ожидалось, или ответ бизнеса по объёму десктоп-редизайна задерживается. Лучше явно заложить буфер здесь, чем незаметно сдвигать релиз без объяснения причины.

**Этап 5. Дискавери (после запуска).** Закрывает цикл — тот же дискавери, что и в начале (этап 0), но уже на реальных данных из прода. Снимаем первый baseline по метрикам из раздела 9 (сейчас в этих таблицах у большинства строк «нет данных» — это и есть повод для этого этапа), сверяем с целями из колонки «Цель после редизайна» и собираем фактический фидбэк от поддержки и агентов. Результат этого этапа — не просто отчёт, а входные данные для следующей итерации: что из раздела 10 сработало, что нет, и что стоит переприоритизировать в P3-фичах (реферальная программа, аффилиат-кабинет, полноценная суб-агентская сеть).
